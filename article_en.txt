SocraticAI: Training Language Models to Give Hints Instead of Answers

Abstract

With the growing popularity of generative AI, especially large language models, students have started using LLMs in programming courses. In our first-year programming course with roughly 600 students, this produced a clear gap between homework and exams. The mean exam score, measured without GenAI access, dropped from 72% to 54%, while average homework grades increased. This pattern does not look like improved understanding. It looks like an illusion of competence: a student can submit externally correct code, but cannot reproduce the reasoning process without an LLM.

A total ban on LLMs is not a stable solution. These tools are already part of modern software practice, and their use outside the classroom is difficult to control. We therefore developed SocraticAI, a family of models trained to respond with guiding hints instead of final answers. SocraticAI is used in Collaborative E-Quiz and OPTMentor, where students may ask for GenAI help during programming work, but the help must remain in the form of hints.

This article focuses on how we train SocraticAI. We describe a synthetic dataset for supervised fine-tuning, a standalone GRPO training script with LLM-as-a-judge reward, and an adversarial curriculum-learning pipeline in which a stronger Red model generates increasingly difficult debugging tasks and incorrect solutions, SocraticAI attempts to produce a useful hint, and a Judge model evaluates both the hint and the task. Hard cases are then fed back into training for SocraticAI and Red.

The main point is that "provide hints, not answers" should not be treated only as prompt engineering. It can be made into a training objective through SFT, GRPO, DPO, execution-based validation, and adversarial curriculum learning. Although our current implementation focuses on Python debugging, the same structure can be transferred to mathematics, SQL, C++, proofs, algorithms, and other courses where students make attempts, produce mistakes, and need guided feedback rather than full solutions.


1. Introduction

In our programming course for 600 first-year students, we observed a worrying pattern. After LLM tools became widely available, the mean score on an exam conducted without GenAI access dropped from 72% to 54%, while grades for homework completed outside class increased. This gap suggests not better learning, but an illusion of competence [1]. A student can submit a correct-looking solution, but may be unable to reproduce the reasoning process without LLM assistance. Programming makes this especially easy: the student can paste generated code, run it, see correct output, and formally finish the task without understanding the logic of the program.

A complete ban on LLMs is not realistic. The use of GenAI outside class is hard to police, and the tools are already part of contemporary engineering practice. The university's task is not only to restrict harmful use, but also to teach productive use. The question, then, is not whether students will use LLMs. The question is how to embed LLMs into the learning process in a way that supports student thinking instead of replacing it.

In our previous work [2, 3], we expressed this as the principle "provide hints, not answers". GenAI should act as a tutor: ask guiding questions, help the student localize the bug, and push the student to repair the program independently. In programming, this means that the model should not write corrected code, should not name a direct line replacement, and should not give a complete solution path. A good hint should be concrete enough to avoid generic advice such as "check your logic", but it should not take the reasoning work away from the student.

To implement this principle, we developed SocraticAI, a family of fine-tuned LLMs for Python and C++. Students can query the model, but the model is trained and constrained to return hints. This article focuses on the training process: supervised fine-tuning on synthetic examples, reinforcement learning with GRPO, and a newer adversarial curriculum-learning pipeline.

The contributions are as follows.

First, we describe the dataset and SFT procedure that teach the model the basic response format: read the task, code, and error, then produce 1-2 guiding questions without revealing the answer.

Second, we describe GRPO training, where the model is optimized not against a single reference hint, but against a reward from a Judge model. The reward combines Socratic style, usefulness, bug localization, technical accuracy, and no solution leakage.

Third, we present an adversarial curriculum-learning pipeline. A Red model generates tasks that expose SocraticAI's current weaknesses; a Judge model evaluates the result; the curriculum increases the probability of weak topics; and difficult cases are fed back into model updates.

Fourth, we show how safety and academic integrity are built into training rather than added only at the interface level. The model is penalized for code output, direct fixes, <think> leakage, jailbreak compliance, and hallucinating bugs when the program actually passes.


2. What Counts as a Socratic Hint

For a regular LLM, the prompt "help me fix this code" naturally becomes a solution. The model may write "replace this condition with ...", "return ... instead", "the bug is ...", or simply provide corrected code. This is convenient, but pedagogically harmful. The student receives an answer without going through the debugging process.

SocraticAI follows a narrower contract. Its answer should:

- be grounded in the concrete code and error;
- ask 1-2 guiding questions;
- help localize where the program state begins to diverge from the expected state;
- avoid corrected code;
- avoid direct replacements;
- avoid a full solution path;
- notice when no error is reproduced instead of inventing a bug.

For example, if an assertion fails because a counter is reset inside a loop, a bad response is: "The bug is that you reset the counter inside the loop. Move it outside." That is already the solution. A better response is: "What value do you expect the counter to have after the second iteration? What actually happens to that variable at the start of each iteration?" The second answer still guides the student, but leaves the reasoning step to them.

In the codebase, this contract appears in the Socratic system prompt in `acl_pipeline/prompts.py`. The model is instructed to respond only with Socratic-style hints and guiding questions, not reveal final code, refuse bypass attempts, and handle the case where no failing assertion or runtime error is reproduced. The user prompt is always built from three blocks: Task, Code, and Error. This matters because the model learns to answer a concrete debugging situation, not an abstract request for help.


3. System Overview

SocraticAI is used inside two educational components.

The first is Collaborative E-Quiz (CE-Quiz), an in-class programming assignment environment. Students solve tasks in class, run their code, and may request GenAI help, but only as hints. This changes the role of GenAI from answer generator to an additional tutor available at the moment the student is stuck.

The second is OPTMentor, a visual in-browser debugger. OPTMentor shows program execution, variable state, and LLM help in the same interface. The student is not interacting with an empty chat box, but with code, a reproduced error, and execution state. This makes it harder for the interaction to collapse into "write the solution for me".

The training stack in the repository has three levels.

The first level is `SFT/SFT.py`. This is a standalone supervised fine-tuning script. It trains a model on examples of the form "prompt -> Socratic hint".

The second level is `GRPO/GRPO.py`. This is a standalone GRPO script. It uses the same prompt format, but instead of a gold hint, the model generates multiple completions and an LLM Judge scores them through an OpenAI-compatible vLLM endpoint.

The third level is `acl_pipeline/`. This is the full adversarial curriculum pipeline. It contains three roles: SocraticAI, Red, and Judge. SocraticAI generates hints. Red generates difficult debugging tasks. Judge evaluates both task quality and hint quality. After each iteration, the pipeline updates SocraticAI and, once enough hard examples exist, also updates Red.

In the current configuration, `configs/default.yaml` initializes SocraticAI from Qwen/Qwen3-1.7B, while Red and Judge use Qwen/Qwen3-32B. Judge can run through a vLLM server, which keeps the larger frozen evaluator separate from the trainable models. SocraticAI is updated through LoRA adapters, which makes the loop cheaper and allows checkpoints to be saved as adapter directories. The config supports both GRPO and DPO for SocraticAI; the current default training method is DPO.


4. Synthetic Dataset and Supervised Fine-Tuning

SFT is not supposed to make the model a perfect tutor. Its first job is more basic: teach the model the correct format. Without SFT, a base model often explains the fix directly, writes corrected code, or produces generic advice not grounded in the error.

The SFT dataset is stored in `SFT/datset_for_SFT.json`. It contains 12,777 synthetic examples. The same records are used in `GRPO/1_final.json`. Each example contains:

- `pronlem` or `problem`: the task statement;
- `code`: buggy program plus tests;
- `observed_failure`: reproduced error or failing assertion;
- `socratic_hints`: target hint;
- metadata such as `sample_id`, `problem_name`, and `type_of_problem`.

In `SFT/SFT.py`, `_build_prompt` converts each record into a prompt with four sections:

Task: the problem statement.
Code: code in a fenced Python block.
Error: the observed failure.
Instruction: ask 1-2 guiding questions without giving the answer.

Then `to_text` adds the system message and assistant completion using the tokenizer's chat template. The loss is computed only over the assistant completion. If the installed TRL version does not provide `DataCollatorForCompletionOnlyLM`, the script uses a fallback collator that finds the assistant prefix and masks labels before the beginning of the answer. This is important: the model is not trained to reproduce the task or code. It is trained to produce the Socratic response.

The script supports full fine-tuning with DeepSpeed ZeRO-2/ZeRO-3, fp16/bf16, gradient checkpointing, evaluation splits, checkpoint cleanup, and compatibility with different TRL versions. It is a production training script rather than a small notebook experiment.

The option `--no-tasks` implements a small SFT curriculum. During the first epoch, the probability of hiding the task statement increases and reaches 1 by 70% of the epoch. In later epochs, the model is trained without the task text. This simulates a harder debugging setting where the statement may be incomplete and the model must rely more on the code and the error. This does not replace debugging reasoning, but it reduces dependence on a perfectly written task statement.

SFT gives a useful starting point, but it has a limitation. The model learns the distribution of hints in the dataset. If the dataset contains overly direct hints, the model becomes too direct. If it contains generic hints, the model becomes generic. This is why we move to reward-based training.


5. GRPO Training

`GRPO/GRPO.py` implements standalone GRPO training. The model no longer receives a target hint. For each prompt, it generates several completions, and a reward function scores each one. In the standard configuration, `num_generations = 4`, max prompt length is 1536, max completion length is 256, and KL beta is 0.02. The script uses LoRA by default and supports full fine-tuning through `--full_ft`. For larger models, it also supports DeepSpeed ZeRO-2/ZeRO-3.

The reward is not a hand-written heuristic. It is produced by a Judge model. The header of the script still mentions a fast heuristic reward, but in the current code the heuristic has been removed: `--judge_model` is required. Judge is called through an OpenAI-compatible endpoint, for example a Qwen3-32B-Instruct model served by vLLM.

The Judge rubric is simple but strict:

- 10: concise guiding questions, no code, no step-by-step solution, student still has to reason;
- 7: helpful and mostly Socratic, but slightly too direct or too long;
- 4: generic or unclear, not tailored to the prompt;
- 0: full solution, explicit fix, final code, or jailbreak compliance.

Jailbreak prompts are part of the reward design. If the user asks the model to ignore instructions or provide the full solution, the correct response is a brief refusal and a redirect back to safe help. Such a refusal should score high if it does not leak the answer.

GRPO can be run in two modes. The first mode starts from the base model, meaning "from scratch" with respect to Socratic training. The second starts from an SFT checkpoint. In practice, SFT-initialized GRPO is usually more stable because the model already knows the answer format, while RL can focus on the difference between a generic hint, a precise hint, and a solution leak.

The advantage of GRPO is that the objective describes pedagogical behavior rather than one reference string. For the same program, many good hints are possible. SFT must choose one. GRPO can reward any answer that remains Socratic and useful.


6. Adversarial Curriculum Learning

SFT and standalone GRPO improve the model, but they still depend on a fixed dataset. Once the dataset stops covering the model's weaknesses, training reaches a plateau. The adversarial curriculum pipeline addresses this by generating new difficult cases during training.

The idea is direct: instead of collecting all tasks in advance, we train SocraticAI in an environment where tasks are generated against it. A stronger Red model produces Python debugging tasks intended to expose current weaknesses. SocraticAI gives a hint. Judge evaluates the hint and the task. Curriculum looks at weak topics and sends Red there more often.

The pipeline is launched by `main.py`, which loads `configs/default.yaml`, configures CUDA visibility, and creates `AdversarialCurriculumPipeline`. One iteration contains the following steps.

1. Curriculum samples a topic.

`CurriculumManager` maintains an EMA reward for each topic. The config includes 15 topics: conditional statements, functions and scope, recursion, dictionaries and sets, sorting, strings, classes, NumPy, decorators, exceptions, mutable state, inheritance, lists/slicing, loops, and arithmetic/type conversion. After each episode, the normalized reward is clipped to [0, 1] and the running reward is updated with alpha = 0.2. The lower the reward for a topic, the higher its sampling weight:

weight(topic) = base_weight * (1 + low_reward_boost * (1 - EMA_reward)).

After each iteration, the weakest topic receives an additional focus boost. If the same topic repeats too many times, the curriculum resets to avoid getting stuck.

2. Red generates a task.

Red receives the topic and a weakness summary, for example: "Recent normalized Socratic reward for 'Sorting and Key Functions' is 0.62. Generate a task that is likely to expose the same weakness more clearly." The prompt requires a strict JSON object with:

- topic;
- target_function;
- intended_bug;
- expected_first_failure;
- statement;
- reference_solution;
- buggy_solution;
- metadata with failure_mode and difficulty.

The important difference from a simple synthetic dataset is that Red must generate both a buggy program and a reference solution. Both programs must contain the same asserts at the end. The reference solution must pass all tests, and the buggy solution must fail at least one shared test because of the intended bug. This makes automatic validation possible.

3. The pipeline validates execution.

In `task_execution.py`, code is executed in isolation with `python -I -B` inside a temporary directory. The reference solution is checked first. If it fails, the task is rejected. Then the buggy solution is checked. If it passes all asserts, the task is rejected as `already_correct_code` or `buggy_too_correct`. Syntax errors, indentation errors, and unrelated name errors can also cause rejection when they do not match the intended bug.

For "buggy too correct" cases, the pipeline runs an assertion audit. It compares reference and buggy behavior on the tests and builds a repair context for Red: which asserts passed, where reference and buggy produced the same values, and why the intended bug did not appear. This makes the repair step concrete rather than simply asking Red to try again.

4. Red repairs invalid tasks.

If a generated task fails validation, the pipeline does not discard it immediately. It appends a repair message with rejection reasons and asks Red for a new strict JSON object. The number of attempts is controlled by `max_red_generation_attempts` and is 4 in the default config. Rejected outputs are stored in `red_rejections.jsonl` and later used for Red DPO training, so Red learns not to repeat those failures.

5. SocraticAI generates hints.

For a valid task, the pipeline builds the Socratic prompt: Task, Code, Error, Instruction. In GRPO mode, one hint is generated. In DPO mode, several candidates are generated (`num_hint_candidates = 4` by default). The raw output is stored, and a sanitized version is also computed. The sanitizer removes `<think>`, code fences, and unsafe long fragments, but Judge scores the raw output. This is intentional: if the model generated a solution leak, it should receive a penalty even if the UI later shows a safe fallback.

6. Judge evaluates task and hint.

Judge is a frozen evaluator. In the default config, it is Qwen/Qwen3-32B served through vLLM. Its rubric scores four tutoring criteria: bug localization, usefulness, Socratic style, and technical accuracy. The default weights are 0.25 each. Judge also returns no_solution_reveal, task_quality, task_is_valid_for_socratic, and hint_is_valid_for_socratic.

The Judge service is not just an LLM prompt. `judge.py` includes local hard rules and feature-based tiebreaks. These detect code-like output, direct fix patterns, `<think>` leakage, corrupted text, mixed scripts, invented identifiers, generic phrases, overly long hints, and too many questions. If a hint contains corrected code or a direct replacement, the score is forced to 0. If the program actually passed, the task is marked invalid, and a good hint must notice that no failure was reproduced. This protects the pipeline from two common failures: bad Red tasks and hallucinated debugging by SocraticAI.

The score is first computed from weighted criteria and then multiplied by a no-solution multiplier. If solution leakage is detected, the multiplier becomes 0.1. Scores are then normalized over a recent window and optionally spread within the batch, which helps preference ranking.

7. SocraticAI is updated.

The pipeline supports two update methods for SocraticAI.

In GRPO mode, `socratic_grpo.py` takes recent episodes, builds a prompt dataset, and launches TRL `GRPOTrainer`. The reward function calls the same Judge service. This is online RL: SocraticAI is optimized directly on tasks recently generated by Red.

In DPO mode, `socratic_dpo.py` uses ranked candidates. For each task, Judge ranks several hints. If the gap between chosen and rejected exceeds `min_score_gap`, the pipeline creates a preference pair. The DPO dataset contains prompt, chosen, and rejected. TRL `DPOTrainer` then updates the LoRA adapter. This mode is cheaper and more stable when the system already generates multiple hint candidates per task.

8. Red is updated.

Red is also trained. The pipeline selects hard examples: valid episodes with low reward, usually the bottom fraction of the iteration and reward <= hard_reward_max. These become chosen completions for Red SFT: "this task successfully exposed a weakness in SocraticAI." Rejected Red outputs become rejected completions for Red DPO. Thus Red learns not merely to generate difficult tasks, but to generate valid tasks that are difficult for the current SocraticAI.

This is where the pipeline becomes adversarial. SocraticAI learns to answer difficult cases better. Red learns to find more useful difficult cases. Curriculum directs both models toward topics where SocraticAI is still weak.


7. Safety and Academic Integrity

Safety in SocraticAI is not a single system prompt. It is layered.

At generation time, SocraticAI receives a clear contract: no final code, no full answer, refuse jailbreaks, ask concise guiding questions. At post-processing time, the sanitizer prevents `<think>` tags, code fences, and obvious direct fixes from reaching the safe UI unchecked. At reward time, Judge penalizes these outputs, which means the model is trained to avoid them rather than merely hidden by the interface.

At task validation time, the pipeline protects training from bad tasks. If Red generates a program that already passes the tests, SocraticAI should not learn to "find" a bug where none exists. If Red generates a syntax error instead of a semantic bug, this is also detected. Such tasks can be rejected or repaired, and rejected outputs become negative training signal for Red.

At classroom deployment time, OPTMentor and CE-Quiz constrain the interaction. The student works inside a programming environment with code, execution trace, and error state. LLM calls go through prompt templates and jailbreak-prevention logic. This does not make cheating impossible, but it changes the default path: it is easier to receive a hint and continue debugging than to receive a finished solution.


8. Classroom Deployment and Evaluation

SocraticAI was embedded into CE-Quiz as part of the in-class programming workflow. Unlike homework, where external LLM use is hard to control, CE-Quiz allows us to set the rule: AI help is allowed, but it must be Socratic. OPTMentor adds the visual debugging layer, so students can connect a hint with the concrete execution state of their program.

The empirical results reported in our INTED 2026 paper are promising, but they should be stated precisely. The intervention was evaluated on a voluntary CE-Quiz group of 60 low-performing students whose midterm score was at most 40%. Among these participants, the proportion scoring above 30% increased from 78.3% on the midterm to 90.0% on the final exam. Their average raw score improvement from midterm to final exam was 16.0 points. In terms of course-wide percentile rank, most students improved by 10-30 percentile points, with a median improvement of 11.9 percentile points. A Wilcoxon signed-rank test rejected the null hypothesis of no systematic rank improvement with p < 0.001.

These numbers should not be read as proof that SocraticAI alone caused all improvement. Real courses contain many moving parts: tasks, student habits, teaching interventions, and familiarity with tools. But the results support the central hypothesis: if GenAI is embedded as a controlled hint generator, it can help students recover the debugging process instead of replacing it.

Small models are also practically important. We release SocraticAI models from 1B to 7B parameters. The 1B models can run locally on a student's laptop without a GPU; the 7B models are suitable for centralized deployment. This reduces cost, latency, and privacy concerns compared with sending student code to large external proprietary LLMs for every request.


9. Generalization Beyond Python

Although the current pipeline is written for Python debugging, its structure is not tied to Python. To transfer it to another course, we need to replace the task schema, the execution or checking function, and the Judge rubric.

In mathematics, Red can generate a problem, an incorrect student solution, and an expected reasoning error. SocraticAI should not write the complete solution. It should ask questions such as: "Which property are you using in this step?", "At which point should the inequality sign change?", or "Why does this transformation preserve equivalence?" Judge would evaluate localization of the reasoning error, usefulness, Socratic style, and mathematical correctness.

In SQL, Red can generate a schema, a target result, and a wrong query. The execution check can run through SQLite. In C++, unit tests can play the role of assertions. In proofs, a rubric-based Judge may be used when automatic checking is difficult. The same idea remains: the student receives a hint that returns them to reasoning, not an answer that replaces reasoning.


10. Limitations

There are several limitations.

First, Judge is itself an LLM. Hard rules, execution validation, and calibrated examples help, but they do not make evaluation perfect. Judge may be too strict toward a good hint or too forgiving toward a polished but weak hint.

Second, adversarial Red may start generating tasks that are formally valid but unlike real student mistakes. Task validation should therefore include not only execution checks, but also human review or course-aligned constraints.

Third, the classroom results are not a randomized controlled trial. They are useful deployment evidence, but they do not replace a stricter measurement of learning gain.

Fourth, SocraticAI does not solve all academic integrity problems. A student can still open an external LLM outside the controlled environment. The goal is not to eliminate GenAI use completely, but to give the course a safe and useful default.


11. Conclusion

SocraticAI shows that GenAI in programming does not have to be an answer generator. If the model is trained and evaluated under a different contract, it can act as a tutor: ask questions, help localize bugs, and keep the student inside the reasoning process.

Technically, this requires more than prompt engineering. SFT gives the model the basic hint format. GRPO optimizes behavior through Judge reward. Adversarial curriculum learning makes training adaptive: Red searches for SocraticAI's weaknesses, Judge evaluates quality, curriculum focuses weak topics, and hard examples feed DPO/GRPO updates.

The pipeline can be transferred to other disciplines. The key requirement is to define what counts as a student attempt, what counts as a mistake, and what kind of hint helps the student think without taking the solution away.
